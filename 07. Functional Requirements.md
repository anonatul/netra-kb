# NETRA — Functional Requirements

> **File:** `07_functional_requirements.md`
> **Status:** Living document
> **Version:** 1.0
> **Last Updated:** 2026-08-17
> **Purpose:** Define testable functional requirements for the NETRA MVP and future system.

---

# 1. Requirement Philosophy

A requirement must describe:

> **What the system must do**

not:

> **What technology the team wants to use.**

Bad requirement:

> "NETRA must use DBSCAN."

Good requirement:

> "NETRA must group spatially related emergency evidence into candidate operational zones while accounting for location uncertainty."

The implementation technology can change without changing the requirement.

---

# 2. Requirement Priority

Each requirement has one of four priorities.

### 🟢 MUST

Required for the MVP/demo.

### 🟡 SHOULD

Important, but can be simplified if time is limited.

### 🔵 COULD

Useful future capability.

### 🔴 WILL NOT

Explicitly excluded from the current scope.

---

# 3. Functional Requirement Structure

Every important requirement should contain:

```text
Requirement ID
Priority
Description
Input
Output
Acceptance Criteria
Failure Behaviour
```

---

# 4. FR-001 — Disaster Context Creation

### Priority

🟢 MUST

### Requirement

NETRA must allow an authorized operator to create or activate a disaster-response context.

### Inputs

* disaster name
* disaster type
* affected geography
* activation time
* operating mode

### Output

```text
Disaster ID
Status = ACTIVE
```

### Acceptance Criteria

The system must:

* create a unique disaster ID
* store disaster type
* store affected geography
* record activation timestamp
* associate incoming incidents with the disaster context

### Failure Behaviour

Invalid disaster configuration must be rejected with an explanatory error.

---

# 5. FR-002 — Emergency Evidence Ingestion

### Priority

🟢 MUST

### Requirement

NETRA must ingest emergency information from supported input sources.

### MVP Sources

At minimum:

* simulated SMS
* simulated emergency reports
* simulated field reports
* structured JSON input

### Future Sources

* ERSS integrations
* authorized emergency location data
* official systems
* sensors
* other authorized sources

### Acceptance Criteria

For every accepted event NETRA must store:

* event ID
* source type
* timestamp
* content
* location if available
* processing status

---

# 6. FR-003 — Source Identification

### Priority

🟢 MUST

NETRA must identify the source type associated with each evidence record.

Example:

```text
SMS
FIELD_REPORT
EMERGENCY_LOCATION
OFFICIAL_SOURCE
SIMULATED
```

### Acceptance Criteria

Every evidence record must have a valid source type.

Unknown sources must be flagged rather than silently categorized.

---

# 7. FR-004 — Evidence Timestamping

### Priority

🟢 MUST

Every incoming evidence record must retain:

* source timestamp if available
* ingestion timestamp
* processing timestamp

### Purpose

This allows NETRA to distinguish:

> when an event happened

from:

> when NETRA received it.

This is essential for degraded connectivity.

---

# 8. FR-005 — Evidence Validation

### Priority

🟢 MUST

NETRA must validate incoming records before processing.

Validation may include:

* required fields
* valid timestamp
* valid coordinates
* allowed payload size
* source authentication where applicable
* schema validity

Invalid records must be logged.

---

# 9. FR-006 — Raw Evidence Preservation

### Priority

🟢 MUST

NETRA must preserve the original evidence reference.

The system may transform evidence for processing, but must not destroy the original record.

### Reason

Every important decision should be traceable to source evidence.

---

### Priority

🟢 MUST

NETRA must transform heterogeneous inputs into a common internal event representation.

### Example

```json
{
  "event_id": "EVT-001",
  "source_type": "SMS",
  "timestamp": "...",
  "text": "...",
  "location": "...",
  "metadata": {}
}
```

The exact schema may evolve.

🟡 SHOULD

* English

```text
Confidence
```

NETRA must extract relevant emergency attributes from supported unstructured messages.

Potential attributes:

* disaster condition
* victim count
* trapped status

# 13. FR-010 — NLP Confidence

### Priority

🟢 MUST

AI-generated attributes must include confidence where technically possible.

Example:

```text
Elderly:
YES

Confidence:
0.94
```

Low-confidence outputs should be flagged.

---

# 14. FR-011 — Rule-Based Fallback

### Priority

🟢 MUST

If the NLP model is unavailable or produces an invalid result, NETRA must fall back to deterministic extraction rules where possible.

Example:

```text
"trapped"
→ trapped = true
```

The fallback must not pretend to provide the same semantic capability as the AI model.

# 16. FR-013 — Duplicate Detection

### Priority

🟢 MUST

NETRA must identify likely duplicate or related reports.

Potential comparison signals:

* spatial proximity
* temporal proximity
* semantic similarity
* incident attributes
* source relationships

# 17. FR-014 — Related-Evidence Linking

### Priority

🟢 MUST

When reports appear related, NETRA must link them to a common incident without deleting the individual evidence records.

Example:

```text
Report A ─┐
Report B ─┼──→ Incident #101

```

# 18. FR-015 — Independent Source Count

### Priority

🟢 MUST

NETRA must distinguish:

> number of reports

from:

> number of independent evidence sources.

Example:

```text
Reports:
25

Independent sources:
8
```

This prevents report spam from being interpreted as independent corroboration.

# 19. FR-016 — Location Processing

### Priority

🟢 MUST

NETRA must process available location evidence.

Possible inputs:

* coordinates
* emergency location
* approximate location
* landmark description
* responder-provided location

---

# 20. FR-017 — Location Confidence

### Priority

🟢 MUST

Every incident with location information should have:

```text
Estimated Location
Confidence
Uncertainty / Accuracy
Source
```

If confidence cannot be calculated reliably, the system must mark it as unknown rather than invent a value.

# 21. FR-018 — Location Uncertainty

### Priority

🟢 MUST

NETRA must support approximate locations.

Example:

```text
Estimated center:
19.0760, 72.8777

Uncertainty:
±250m
```

The UI should visually distinguish uncertain areas from precise locations.

---

# 22. FR-019 — Text-Based Location Extraction

### Priority

🟡 SHOULD

NETRA should extract locations from messages such as:

> "Near the old railway bridge."

The result should contain:

```text

Confidence
Source Text
```

Ambiguous locations must be flagged for review.

# 23. FR-020 — Evidence Fusion

### Priority

🟢 MUST

NETRA must combine multiple evidence records associated with the same incident.

The fused incident should preserve:

* source diversity
* source count
* timestamps
* location evidence
* extracted attributes
* field verification

🟢 MUST

```text
HIGH
MEDIUM
```

# 25. FR-022 — Confidence Explanation

🟢 MUST

# 26. FR-023 — Incident Freshness

### Priority

🟢 MUST

NETRA must track how recently relevant evidence was received.

Possible categories:

```text
FRESH
RECENT
STALE
UNKNOWN
```

The thresholds should be disaster/configuration dependent.

# 27. FR-024 — No-Signal Safety Rule

### Priority

🟢 MUST

NETRA must never automatically classify an incident as safe merely because no new report has arrived.

Silence may indicate:

* rescue
* communications failure
* device failure
* battery depletion
* inability to report
* continued emergency

---

# 28. FR-025 — Spatial Clustering

### Priority

🟢 MUST

NETRA must group related incidents into operational zones.

The clustering mechanism must support location uncertainty.

# 29. FR-026 — Cluster Confidence

# 32. FR-029 — Rescue Priority

### Priority

🟢 MUST

NETRA must assign a rescue priority to incidents or operational zones.

Initial conceptual levels:

```text
P1 — CRITICAL
P2 — HIGH
P3 — MODERATE
P4 — LOW / MONITOR
```

# 33. FR-030 — Priority Factors

### Priority

🟢 MUST

Priority calculation should consider relevant factors such as:

* severity
* victim count
* vulnerability
* recency
* evidence confidence
* location confidence
* accessibility

Not every factor must have equal weight.

Weights must be validated.

# 35. FR-032 — Priority Score Versioning

🟡 SHOULD

# 47. FR-044 — Field Verification

🟢 MUST

# 48. FR-045 — Incident Reconciliation

### Priority

🟡 SHOULD

If field evidence conflicts with automated inference, the system should preserve both and mark the conflict.

Example:

```text
AI:
Victims = 30

Field:
Victims = 12

Status:
CONFLICTING EVIDENCE
```

Human review resolves the operational state.

---

# 49. FR-046 — Offline Local Operation

### Priority

🟢 MUST for MVP

NETRA must continue basic operation when the command centre loses internet connectivity.

Minimum offline functionality:

* view cached incidents
* process locally available data
* update incident status
* display map
* calculate priority
* store changes locally

---

# 50. FR-047 — Offline Synchronization

### Priority

🟡 SHOULD

When connectivity returns, locally generated updates should synchronize with the central system.

Potential conflict:

```text
Central update
+
Offline update
```

The system must preserve timestamps and resolve conflicts according to defined rules.

---

# 51. FR-048 — Graceful AI Degradation

### Priority

🟢 MUST

If AI services fail:

```text
AI unavailable
      ↓
Rule-based extraction
      ↓
Reduced-confidence result
      ↓
Human review where necessary
```

The emergency workflow must continue.

---

# 52. FR-049 — Graceful Location Degradation

### Priority

🟢 MUST

If precise location is unavailable:

```text
Exact coordinate
      ↓
Approximate coordinate
      ↓
Area / landmark
      ↓
Unknown
```

Confidence must decrease accordingly.

---

# 53. FR-050 — Graceful Priority Degradation

### Priority

🟢 MUST

If the advanced priority model fails, NETRA must provide a simpler fallback.

Example:

```text
Severity
+
Victim Count
+
Recency
```

This is preferable to total system failure.

---

# 54. FR-051 — Audit Logging

### Priority

🟢 MUST

NETRA must log important actions:

* incident creation
* priority changes
* human overrides
* field verification
* status changes
* recommendations
* user actions

# 55. FR-052 — User Authentication

### Priority

🟢 MUST

Authorized users must authenticate before accessing responder functionality.

# 56. FR-053 — Role-Based Access Control

### Priority

🟢 MUST

Different users should receive appropriate permissions.

### Priority

🟢 MUST

NETRA must protect sensitive emergency information.

* access control

🟡 SHOULD

The system should support configurable retention policies.

🟢 MUST

# 60. FR-057 — Duplicate Incident Merge

Authorized users should be able to merge incidents when automated consolidation is incorrect or incomplete.

# 63. FR-060 — Filtering

# 64. FR-061 — Alerting

### Priority

🟡 SHOULD

NETRA should notify authorized users when:

* new P1 incident appears
* P2 becomes P1
* critical field update arrives
* large incident burst occurs
* system confidence changes significantly

Alerts must be rate-limited to avoid alert fatigue.

# 65. FR-062 — Alert Fatigue Protection

### Priority

🟢 MUST

NETRA must avoid generating hundreds of redundant alerts from the same incident.

Related events should be grouped.

---

# 66. FR-063 — System Health Monitoring

🟡 SHOULD

* ingestion status

# 77. FR-074 — Priority Stability

### Priority

🟡 SHOULD

NETRA should avoid unnecessary priority oscillation caused by minor evidence changes.

Potential mechanisms:

* hysteresis
* confidence thresholds
* minimum score change
* human confirmation for repeated changes

The exact method requires experimentation.

🟡 SHOULD

🟡 SHOULD

NETRA should support configurable source reliability metadata.

Example:

```text

HIGH
```

# 82. FR-079 — Privacy-Preserving Identity

### Priority

🟢 MUST

The system should use the minimum identity information necessary for emergency operations.

Where identity is not operationally required, the system should prefer:

* pseudonymous IDs
* hashed identifiers
* role-based access
* controlled disclosure

---

# 83. FR-080 — Data Access Audit

### Priority

🟡 SHOULD

# 84. FR-081 — System Recovery

### Priority

🟢 MUST

After application restart, NETRA must recover:

* active incidents
* priority states
* evidence
* pending updates
* audit history

No critical state should exist only in volatile memory.

---

# 85. FR-082 — Backpressure

### Priority

🟡 SHOULD

If incoming event volume exceeds processing capacity, NETRA should:

* queue events
* preserve timestamps
* process according to defined priority
* expose backlog
* avoid dropping critical events silently

---

# 86. FR-083 — Critical Event Priority

### Priority

🟡 SHOULD

Potentially critical events should receive processing preference during high-load conditions.

Example:

```text
Building collapse
Medical emergency
Trapped victims
```

However, the system must not rely on unvalidated keyword matching alone.

---

# 87. FR-084 — No Autonomous Life-Critical Action

### Priority

🟢 MUST

NETRA must never independently:

* dispatch emergency vehicles
* declare a person safe
* cancel a rescue
* close an incident as resolved
* override a human commander

without explicit authorized human workflow.

---

# 88. FR-085 — Explainable Failure

### Priority

🟢 MUST

When NETRA cannot confidently process an event, it should show:

```text
Status:
UNRESOLVED

Reason:
Location ambiguous

Action:
Human review required
```

It should not generate fabricated certainty.

---

# 89. FR-086 — Uncertainty Propagation

### Priority

🟢 MUST

If an important input is uncertain, downstream outputs should reflect that uncertainty.

Example:

```text
Location confidence:
LOW

→ Cluster confidence:
LOW

→ Incident confidence:
MEDIUM

→ Priority:
Requires review
```

The system should not turn uncertain input into highly confident output without justification.

---

# 90. FR-087 — Evidence-Based Recalculation

### Priority

🟢 MUST

When new evidence changes a major incident attribute, NETRA must recalculate dependent outputs.

Example:

```text
Victims:
10 → 40

Therefore:
Priority recalculated
Resource recommendation recalculated
```

---

# 91. FR-088 — Manual Evidence Addition

### Priority

🟢 MUST

Authorized responders should be able to add structured field evidence.

---

# 92. FR-089 — Manual Incident Creation

### Priority

🟢 MUST

Authorized operators must be able to manually create an incident when information comes through a channel not integrated with NETRA.

This prevents NETRA from becoming useless simply because a source is not digitally integrated.

---

# 93. FR-090 — Manual Priority Assignment

### Priority

🟢 MUST

Authorized responders should be able to assign or modify priority manually.

The system should record the reason.

# 95. Requirements That Should NOT Drive MVP

The following are useful but should not distract from the core demonstration:

* advanced predictive analytics
* satellite-image intelligence
* complex IoT integration
* nationwide external integrations
* sophisticated route optimization
* autonomous resource dispatch
* advanced forecasting
* unnecessary generative-AI features
* custom communication infrastructure

# 97. Acceptance-Test Principle

A requirement is not complete because:

> "The code exists."

It is complete when:

> **A repeatable test demonstrates that the required behaviour works.**

---

# 98. Requirement Quality Rules

Every requirement should be:

### Specific

No vague language.

### Testable

There must be an acceptance condition.

### Traceable

It maps to a component and test.

### Minimal

Avoid unnecessary requirements.

### Evidence-based

Do not invent operational requirements.

# 99. Final Functional Requirement Summary

NETRA's functional requirements can be grouped into eight capability families:

```text
1. INGEST
   Receive emergency evidence

2. UNDERSTAND
   Extract structured incident information

3. CONSOLIDATE
   Link duplicate/related evidence

4. LOCATE
   Estimate location and uncertainty

5. PRIORITIZE
   Rank incidents/zones

6. RECOMMEND
   Suggest response resources

7. OPERATE
   Support responders and field verification

8. SURVIVE FAILURE
   Continue through degraded AI,
   location, connectivity and service conditions
```

---

# 100. Final Functional Definition

> **NETRA must ingest heterogeneous emergency evidence, transform it into structured incidents, preserve and fuse supporting evidence, estimate location and confidence, consolidate related incidents into operational zones, calculate explainable disaster-specific rescue priorities, recommend potential response resources, support human responder decisions and field verification, and continue operating safely through partial technology failures.**

---

# 101. Golden Requirement Rule

> **If a requirement cannot be demonstrated, tested, measured, or traced to a real operational need, it should not be treated as a core NETRA requirement.**
