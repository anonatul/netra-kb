> **File:** `08_non_functional_requirements.md`
> **Status:** Living document

> **Purpose:** Define measurable quality, reliability, security, performance, scalability, resilience, privacy, and operational requirements for NETRA.

---

# 1. Why Non-Functional Requirements Matter

A disaster-response system cannot be judged only by:

> "Does the feature work?"

The more important questions are:

* How fast does it respond?
* What happens when connectivity fails?
* What happens when AI fails?
* Can it process a sudden report surge?
* Can operators trust its recommendations?
* Can sensitive emergency data be protected?
* Can the system recover after a crash?
* Can every important decision be audited?
* Does uncertainty propagate correctly?
* Can the system remain usable under stress?

These requirements define whether NETRA can move from:

> **hackathon prototype**

to:

> **credible operational system.**

---

# 2. Requirement Classification

Each non-functional requirement has one of four priorities.

### 🟢 MUST

Required for a credible MVP.

### 🟡 SHOULD

Important for a stronger prototype or pilot.

### 🔵 COULD

Production enhancement.

### 🔴 WILL NOT

Explicitly outside the current project scope.

---

# 3. Important Rule About Numbers

The team must not invent impressive performance numbers just for the pitch.

For example:

> "NETRA supports 1 million reports per second."

is meaningless without a benchmark.

Instead:

> "NETRA processed X events/sec in our controlled load test on Y hardware."

Therefore every numerical target should eventually have:

```text
Metric
Test Method
Hardware
Dataset
Observed Result
```

---

# 4. NFR-001 — End-to-End Processing Latency

### Priority

🟢 MUST

NETRA should process a normal emergency event from ingestion to initial structured incident representation within a bounded latency.

The exact target must be benchmarked.

Suggested MVP target:

> **P95 ≤ 5 seconds** for simulated normal-load events excluding external integration latency.

This is a proposed engineering target, not a real-world guarantee.

---

# 5. NFR-002 — Priority Generation Latency

### Priority

🟢 MUST

After sufficient evidence is available, NETRA should calculate or update incident priority within a predictable time.

Suggested MVP target:

> **P95 ≤ 2 seconds** for local priority recalculation.

The benchmark should exclude human review time.

---

# 6. NFR-003 — Dashboard Response Time

### Priority

🟢 MUST

Common responder actions should remain responsive.

Examples:

* opening incident
* filtering incidents
* changing map view
* viewing evidence
* updating status

Suggested target:

> **P95 ≤ 2 seconds** for common local dashboard operations.

---

# 7. NFR-004 — AI Processing Latency

### Priority

🟡 SHOULD

NLP processing should have measurable latency.

The benchmark should report:

```text
Average
P50
P95
P99
```

The system should not hide slow AI inference behind an artificial frontend loading state.

---

# 8. NFR-005 — Graceful AI Degradation

### Priority

🟢 MUST

If the AI/NLP service becomes unavailable:

```text id="0x9l7m"
AI unavailable
      ↓
Fallback rules
      ↓
Lower-confidence structured result
      ↓
Human review where needed
```

The core emergency workflow must continue.

---

# 9. NFR-006 — Availability

### Priority

🟡 SHOULD

For a production deployment, NETRA should target high availability.

For the SIH MVP:

> **Demonstrate recovery rather than claim production availability.**

The demo should show that a service restart does not destroy active incident state.

---

# 10. NFR-007 — Crash Recovery

### Priority

🟢 MUST

After application failure and restart, NETRA must recover:

* active incidents
* evidence
* priorities
* status
* pending updates
* audit records

Critical state must not depend solely on in-memory storage.

---

# 11. NFR-008 — Data Durability

### Priority

🟢 MUST

Accepted emergency evidence must be persisted reliably.

A successful API response should not mean:

> "We will save it later."

The system should define when an event is considered durably accepted.

---

# 12. NFR-009 — No Silent Data Loss

### Priority

🟢 MUST

If NETRA cannot process an event, it must:

* preserve the event
* record the failure
* expose the processing state
* retry or route to fallback processing

It must not silently discard emergency information.

---

# 13. NFR-010 — Idempotent Processing

### Priority

🟢 MUST

Repeated delivery of the same event must not create uncontrolled duplicate incidents.

Example:

```text id="9x7s2v"
Event EVT-100
      ↓
Received twice
      ↓
One logical event
```

This is particularly important for retry-based systems.

---

# 14. NFR-011 — Event Ordering

### Priority

🟡 SHOULD

NETRA should preserve source timestamps and handle events arriving out of order.

Example:

```text id="x5z9w2"
Event A:
10:10

Event B:
10:08

Received:
B after A
```

The system must not assume:

> ingestion order = event order.

---

# 15. NFR-012 — Clock Handling

### Priority

🟡 SHOULD

The system should use consistent time handling.

Recommended:

* UTC internally
* local timezone for user-facing display
* explicit source timestamp
* explicit ingestion timestamp

---

# 16. NFR-013 — Offline Operation

### Priority

🟢 MUST

The local NETRA deployment should continue core operations when internet connectivity is unavailable.

At minimum:

* view cached data
* process locally available events
* calculate priority
* update incidents
* store local changes

---

# 17. NFR-014 — Offline Data Persistence

### Priority

🟢 MUST

Offline-generated updates must survive:

* temporary power interruption
* application restart
* temporary network failure

assuming the underlying device/storage remains available.

---

# 18. NFR-015 — Synchronization After Reconnection

### Priority

🟡 SHOULD

When connectivity returns:

```text id="m6d8x3"
Local changes
      ↓
Sync
      ↓
Conflict detection
      ↓
Central state
```

The system should not simply overwrite one side blindly.

---

# 19. NFR-016 — Conflict Resolution

### Priority

🟡 SHOULD

Conflicting updates should preserve:

* both timestamps
* source
* user
* previous state
* new state

Example:

```text id="q7m2c5"
Central:
Road blocked

Field:
Road accessible

→ CONFLICT
```

A human or defined conflict policy resolves the operational state.

---

# 20. NFR-017 — Connectivity Awareness

### Priority

🟢 MUST

NETRA should display operating status:

```text id="v7y5q1"
ONLINE
DEGRADED
OFFLINE
SYNCING
```

Operators must know whether they are seeing live or locally cached information.

---

# 21. NFR-018 — Staleness Transparency

### Priority

🟢 MUST

The interface must indicate how recent information is.

Example:

```text id="7b5q9x"
Last evidence:
4 minutes ago
```

rather than presenting the incident as continuously current.

---

# 22. NFR-019 — Scalability

### Priority

🟡 SHOULD

NETRA should be able to handle increasing:

* reports
* incidents
* geographic zones
* users
* disaster contexts

The architecture should avoid assumptions that only one disaster or a few hundred reports will exist.

---

# 23. NFR-020 — Load Testing

### Priority

🟢 MUST

The team should conduct controlled load testing.

At minimum test:

```text id="v5x8j2"
Normal load
2× normal load
5× normal load
10× burst load
```

Measure:

* throughput
* latency
* error rate
* CPU
* memory
* queue depth

---

# 24. NFR-021 — Burst Handling

### Priority

🟢 MUST

NETRA should handle sudden report spikes without silently losing events.

Example:

```text id="f8q4m1"
100 events/min
       ↓
5,000 events/min
```

The system should:

* queue
* process
* expose backlog
* preserve timestamps
* prioritize critical processing where appropriate

The actual capacity must be benchmarked.

---

# 25. NFR-022 — Backpressure

### Priority

🟡 SHOULD

When processing capacity is exceeded, NETRA should apply controlled backpressure rather than allowing the entire system to collapse.

Potential mechanisms:

* queueing
* rate limiting
* batch processing
* priority-aware scheduling

---

# 26. NFR-023 — Horizontal Scalability

### Priority

🔵 COULD

Production architecture should allow stateless processing components to scale horizontally.

However:

> **Do not introduce Kubernetes or microservices merely to claim scalability.**

For the MVP, a modular monolith can be entirely appropriate.

---

# 27. NFR-024 — Database Scalability

### Priority

🟡 SHOULD

The database should support:

* indexed incident queries
* spatial queries
* timestamp filtering
* priority filtering
* historical records

The exact database technology should be chosen based on workload.

---

# 28. NFR-025 — Spatial Query Performance

### Priority

🟢 MUST

Common map queries should remain responsive for the expected MVP dataset.

Examples:

* incidents within viewport
* incidents within radius
* incidents within disaster boundary
* priority zones in area

Spatial indexes should be used where appropriate.

---

# 29. NFR-026 — Security in Transit

### Priority

🟢 MUST

Communication between clients and backend should use secure transport.

Production deployments should use:

> **TLS / HTTPS**

No sensitive emergency information should be transmitted through plaintext application protocols.

---

# 30. NFR-027 — Encryption at Rest

### Priority

🟡 SHOULD

Sensitive stored information should be encrypted at rest where required by deployment policy.

The exact encryption architecture depends on infrastructure.

---

# 31. NFR-028 — Authentication

### Priority

🟢 MUST

Responder-facing interfaces must require authentication.

Anonymous access to operational incident data is unacceptable.

---

# 32. NFR-029 — Authorization

### Priority

🟢 MUST

Users should only have access to operations appropriate to their role.

Example:

```text id="k6x3r8"
Operator:
View + update incidents

Commander:
View + priority override

Field responder:
Field verification

Administrator:
System configuration
```

---

# 33. NFR-030 — Least Privilege

### Priority

🟢 MUST

Every account and service should receive only the permissions necessary for its function.

---

# 34. NFR-031 — Session Security

### Priority

🟡 SHOULD

Production authentication should support:

* secure session management
* expiration
* revocation
* protection against token theft
* secure credential storage

---

# 35. NFR-032 — Auditability

### Priority

🟢 MUST

Important actions must be recorded.

Examples:

* login
* incident access
* priority change
* manual override
* evidence addition
* incident resolution
* resource recommendation
* administrative change

---

# 36. NFR-033 — Audit Integrity

### Priority

🟡 SHOULD

Audit logs should be protected from unauthorized modification.

At minimum:

* restricted access
* timestamps
* actor identity
* immutable/append-only strategy where practical

---

# 37. NFR-034 — Privacy

### Priority

🟢 MUST

NETRA should follow data-minimization principles.

Only information required for:

* emergency response
* verification
* operational coordination
* auditing

should be retained.

---

# 38. NFR-035 — PII Protection

### Priority

🟢 MUST

Personally identifiable information should not be unnecessarily exposed in the dashboard.

Where possible use:

```text id="8d3x4p"
Pseudonymous ID
+
Role
+
Required operational information
```

rather than displaying full personal information everywhere.

---

# 39. NFR-036 — Sensitive Location Protection

### Priority

🟢 MUST

Emergency locations can be highly sensitive.

Access should be restricted according to user role.

Public-facing interfaces should not expose precise victim locations by default.

---

# 40. NFR-037 — Data Retention

### Priority

🟡 SHOULD

Retention periods must be configurable and aligned with applicable:

* government policies
* legal requirements
* organizational policies
* operational requirements

The team should not invent a universal retention period.

---

# 41. NFR-038 — Model Accuracy

### Priority

🟢 MUST

Every AI capability must have an evaluation metric.

Examples:

### Classification

* precision
* recall
* F1

### Location extraction

* exact match
* distance error

### Victim extraction

* precision
* recall
* MAE where appropriate

---

# 42. NFR-039 — False Positive Control

### Priority

🟢 MUST

NETRA must explicitly measure false-positive rates for critical classifications.

Example:

> incorrectly marking an incident as P1.

This can be operationally dangerous.

---

# 43. NFR-040 — False Negative Control

### Priority

🟢 MUST

NETRA must measure false negatives for critical events.

Example:

> failing to recognize a trapped-victim emergency.

For high-risk categories, false negatives may be more dangerous than false positives.

The system should not optimize for one metric alone.

---

# 44. NFR-041 — Uncertainty Representation

### Priority

🟢 MUST

Uncertain outputs must be represented explicitly.

Examples:

```text id="6x4q9p"
Location confidence:
LOW

Victim count:
12–20

Severity:
MEDIUM confidence
```

The system should not manufacture exact numbers from uncertain evidence.

---

# 45. NFR-042 — Confidence Calibration

### Priority

🟡 SHOULD

If NETRA displays probabilities, those probabilities should eventually be calibrated against observed outcomes.

A model saying:

> "90% confidence"

should eventually mean something measurable.

Until validated:

> use qualitative confidence labels where appropriate.

---

# 46. NFR-043 — Explainability

### Priority

🟢 MUST

Critical decisions must have understandable explanations.

The system should expose:

* major factors
* evidence
* model/rule version
* confidence
* human overrides

---

# 47. NFR-044 — Reproducibility

### Priority

🟡 SHOULD

Given:

```text id="k3w6f8"
Same input
+
Same model version
+
Same rules
```

NETRA should produce substantially reproducible results.

This is important for testing and audit.

---

# 48. NFR-045 — Model Versioning

### Priority

🟢 MUST

AI outputs must be associated with a model version.

Example:

```text id="x7h2j4"
NETRA-NLP
v1.2.0
```

---

# 49. NFR-046 — Rule Versioning

### Priority

🟢 MUST

Priority and recommendation rules must be versioned.

Example:

```text id="j5f7q2"
Priority Rules:
v1.1
```

---

# 50. NFR-047 — Safe Model Deployment

### Priority

🟡 SHOULD

A new model should not automatically become production-critical without validation.

Potential process:

```text id="9v4q7k"
New Model
   ↓
Offline Evaluation
   ↓
Benchmark
   ↓
Expert Review
   ↓
Controlled Deployment
```

---

# 51. NFR-048 — Human Override Reliability

### Priority

🟢 MUST

Human overrides must always take precedence over automated recommendations within authorized permissions.

---

# 52. NFR-049 — No Hidden Automation

### Priority

🟢 MUST

The UI must clearly indicate whether a value was:

* manually entered
* extracted by AI
* calculated by rules
* estimated from multiple sources
* verified by a responder

---

# 53. NFR-050 — Observability

### Priority

🟢 MUST

Operators/developers must be able to determine system health.

At minimum monitor:

* event ingestion rate
* processing latency
* queue backlog
* error rate
* database health
* AI service health
* synchronization status

---

# 54. NFR-051 — Structured Logging

### Priority

🟢 MUST

System logs should be structured and machine-readable.

Logs should include:

* timestamp
* service/component
* event ID
* severity
* error code
* correlation ID

Sensitive personal information should not be unnecessarily written into logs.

---

# 55. NFR-052 — Correlation IDs

### Priority

🟡 SHOULD

A single event should be traceable across:

```text id="h5n3k2"

 ↓
NLP
 ↓
Fusion
 ↓
Priority
 ↓
Dashboard
```

# 56. NFR-053 — Error Classification

### Priority

🟢 MUST

```text id="c9v7d1"

AUTHENTICATION_ERROR
DEPENDENCY_FAILURE
```

# 57. NFR-054 — Recovery Time

### Priority

🟡 SHOULD

For the MVP, define and test recovery time after a simulated service failure.

Example metric:

> Time from service crash to restored processing.

Do not claim a production SLA without infrastructure to support it.

---

# 58. NFR-055 — Recovery Point

### Priority

🟡 SHOULD

The team should measure how much accepted data could be lost after failure.

> **No acknowledged critical incident state lost in the normal failure scenario.**

# 59. NFR-056 — Backup

# 61. NFR-058 — Resource Efficiency

### Priority

🟡 SHOULD

* CPU usage
* memory
* storage
* network bandwidth
* AI inference cost

This is especially important if deployment occurs on limited hardware.

---

# 62. NFR-059 — Local Hardware Viability

### Priority

🟢 MUST

The MVP should demonstrate that core NETRA processing can operate on realistic command-center hardware.

The team must document:

```text id="3b5x7n"

RAM

```

# 63. NFR-060 — AI Hardware Independence

### Priority

🟡 SHOULD

The system should have a fallback mode when GPU acceleration is unavailable.

This prevents:

> "NETRA cannot operate because there is no GPU."

---

# 64. NFR-061 — Bandwidth Efficiency

### Priority

🟡 SHOULD

The system should minimize unnecessary data transfer during degraded connectivity.

Examples:

* incremental sync
* compressed payloads
* local caching
* delta updates

---

# 65. NFR-062 — UI Usability Under Stress

### Priority

🟢 MUST

The responder UI must prioritize:

* high contrast
* clear priority hierarchy
* minimal navigation
* obvious status
* visible uncertainty
* low interaction count

A disaster dashboard should not look like an analytics platform.

---

# 66. NFR-063 — Cognitive Load

### Priority

🟢 MUST

The system should reduce rather than increase the number of items requiring manual inspection.

This should eventually be evaluated experimentally.

Potential metric:

> Number of raw reports manually inspected before identifying top-priority incidents.

---

# 67. NFR-064 — Accessibility

### Priority

🟡 SHOULD

The interface should support:

* keyboard navigation
* readable typography
* accessible color/shape indicators
* clear labels
* non-color-only status indicators

---

# 68. NFR-065 — Localization

### Priority

🟡 SHOULD

The responder interface should eventually support relevant regional languages.

However:

> multilingual UI is secondary to reliable multilingual incident understanding.

---

# 69. NFR-066 — Browser Resilience

### Priority

🟢 MUST

If the dashboard is browser-based, it should recover gracefully from:

* temporary backend failure
* network interruption
* stale sessions
* synchronization delays

---

# 70. NFR-067 — Security Failure Behaviour

### Priority

🟢 MUST

Security failures should fail closed.

Examples:

```text id="r5g2q8"
Invalid authentication

Insufficient permission

```

The system should never fall back to anonymous privileged access.

---

# 71. NFR-068 — Rate Limiting

🟡 SHOULD

* accidental overload

---

# 72. NFR-069 — Input Sanitization

### Priority

🟢 MUST

* text
* coordinates
* identifiers
* API payloads

---

# 73. NFR-070 — Secure Dependency Management

### Priority

🟡 SHOULD

The project should track:

* dependency versions
* known vulnerabilities

# 102. NFR-099 — Observable AI Failure

### Priority

🟢 MUST

If AI is unavailable, the UI must indicate:

```text id="m6r2v8"
NLP:
DEGRADED

Fallback:
RULE ENGINE
```

Never silently downgrade while pretending the AI model is active.

# 103. NFR-100 — System Integrity

### Priority

🟢 MUST

NETRA must maintain consistency between:

* incident state
* evidence
* priority
* recommendation
* field updates
* audit records

An update to one component must not leave the system in an impossible state.

# 105. What NOT to Promise

Do not say:

> "99.9999% availability."

unless infrastructure supports it.

Do not say:

> "Processes millions of events."

unless load testing proves it.

Do not say:

> "AI is 99% accurate."

unless evaluation proves it.

Do not say:

> "Works during complete network failure."

unless the communication architecture actually supports it.

Do not say:

> "Zero false positives."

No realistic emergency intelligence system can guarantee this.

# 107. NFR Failure Philosophy

NETRA should follow:

```text id="k8x2d5"
UNKNOWN
    >
LOW CONFIDENCE
    >
HUMAN REVIEW
    >
FALSE CERTAINTY
```

The worst failure is not:

> "The system says I don't know."

The worst failure is:

> **"The system confidently tells responders something false."**

---

# 108. Security Philosophy

NETRA should follow:

```text id="6n3p7x"
AUTHENTICATE
     ↓
AUTHORIZE
     ↓
MINIMIZE DATA
     ↓
ENCRYPT
     ↓
AUDIT
     ↓
MONITOR
```

Security is not an optional add-on.

# 109. Reliability Philosophy

NETRA should follow:

```text id="f5v8q2"
Preferred Service
      ↓
Failure
      ↓
Fallback
      ↓
Reduced Capability
      ↓
Human Review
```

Never:

```text id="w4m1n7"
Preferred Service
      ↓
Failure
      ↓
Entire Emergency Workflow Stops
```

# 110. Scalability Philosophy

The correct order is:

```text id="9q6r4s"
Prove correctness
      ↓
Measure performance
      ↓
Identify bottleneck
      ↓
Optimize
      ↓
Scale where necessary
```

Not:

```text id="u8m5k2"
Add Kafka
+
Redis
+
Kubernetes
+
Microservices
+
Cloud
```

without evidence that they solve a real bottleneck.

# 111. Final Non-Functional Definition

> **NETRA must be responsive, resilient, auditable, secure, privacy-conscious, uncertainty-aware and capable of continuing essential operations under partial technology failure. Its critical outputs must be traceable to evidence, its AI components must have measurable performance and safe fallbacks, and its production claims must be supported by reproducible benchmarks rather than assumptions.**

---

# 112. Golden NFR Rule

> **In an emergency system, reliability is not the absence of failure; reliability is the ability to fail safely, preserve evidence, remain useful, and clearly communicate uncertainty.**
