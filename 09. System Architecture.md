# 1. Architecture Objective

NETRA's architecture must satisfy five competing requirements:

1. **Simple enough to build within SIH constraints**
2. **Reliable enough to demonstrate emergency-system thinking**
3. **Modular enough to evolve**
4. **Offline-capable at the local command-centre level**
5. **Scalable toward future institutional deployment**

The architecture must therefore avoid both extremes:

### Extreme A — Too simple

```text
Frontend
   ↓
One giant API
   ↓
Database
```

This can become difficult to evolve and test.

### Extreme B — Overengineered

```text
Frontend
 ↓
API Gateway
 ↓
Kafka
 ↓
10 Microservices
 ↓
Redis
 ↓
RabbitMQ
 ↓
Kubernetes
 ↓
Multiple databases
 ↓
Service mesh
```

This is unnecessary for an SIH MVP.

# 3. Core Architectural Principle

The architecture is organized around:

> **Domain capabilities, not technologies.**

The system should be able to replace:

* NLP model
* clustering algorithm
* priority model
* external data adapter

without rewriting the entire platform.

# 6. Frontend Design Principle

The dashboard is not a generic analytics dashboard.

It should optimize:

> **Decision speed under cognitive stress.**

The primary screen should answer:

```text

WHERE IS IT?
WHY IS IT IMPORTANT?
HOW CONFIDENT ARE WE?
WHAT SHOULD I CONSIDER DOING?
```

# 8. Backend

The backend should initially be a **modular monolith**.

This means:

> One deployable backend application with clearly separated internal modules.

Example:

```text
backend/
├── auth/
├── ingestion/
├── incidents/
├── evidence/
├── location/
├── fusion/
├── clustering/
├── priority/
├── recommendations/
├── field/
├── audit/
└── simulation/
```

This provides modularity without distributed-system complexity.

---

# 9. Why Modular Monolith?

For SIH:

### Advantages

* faster development
* simpler deployment
* easier debugging
* fewer network failures
* simpler transactions
* easier offline deployment
* easier demo
* lower infrastructure cost

### Disadvantages

* less independent scaling
* large codebase if poorly structured
* future extraction may be required

These disadvantages are manageable at MVP scale.

---

# 10. When to Introduce Microservices

Microservices should only be introduced if there is evidence for a real need.

Examples:

### NLP service

Separate it if:

* inference requires dedicated hardware
* model deployment cadence differs
* inference scaling differs significantly

### Ingestion service

Separate it if:

* event volume becomes very high
* multiple external integrations require isolation

### Analytics service

Separate it if:

* historical analytics workloads interfere with operational processing

Until then:

> Keep them modular inside the same application.

# 15. Synchronous vs Asynchronous Processing

Not every operation should block the API request.

### Synchronous

Good for:

* authentication
* simple incident retrieval
* field status update
* dashboard queries
* simple priority retrieval

### Asynchronous

Better for:

* NLP
* large-scale deduplication
* batch clustering
* analytics
* bulk imports
* scenario replay

# 16. MVP Queue Strategy

For the MVP, a lightweight job queue may be sufficient.

Possible implementation:

```text
API
 ↓
Job Queue
 ↓
Worker
 ↓
Processing
```

The specific queue technology should be selected based on implementation constraints.

Do not add Kafka solely because:

> "Kafka is scalable."

---

# 17. Why Not Kafka for MVP?

Kafka is powerful but introduces:

* operational complexity
* configuration overhead
* additional failure modes
* monitoring requirements
* deployment complexity

If the MVP processes a few thousand simulated events:

> **Kafka is probably unnecessary.**

A simpler queue or database-backed job system may be sufficient.

---

# 18. Why Not RabbitMQ + Kafka?

Using both without a demonstrated requirement is unnecessary.

Choose:

> **one appropriate mechanism**

based on workload.

---

# 19. Database

Recommended primary database:

> **PostgreSQL + PostGIS**

Reasons:

* relational consistency
* mature ecosystem
* geospatial support
* spatial indexes
* strong transaction support
* easy local deployment
* suitable for incident data

---

# 20. Why PostGIS?

NETRA is inherently spatial.

Common operations include:

```text
Find incidents within radius
Find incidents inside disaster polygon
Calculate distances
Group nearby incidents
Query operational zones
```

PostGIS provides mature support for these operations.

These must remain separate.

### Event

A raw incoming observation.



# 29. Priority Engine Principle

The engine should be deterministic wherever possible.

For the MVP:

> Prefer explainable rules before complex ML.

Example:

```text
IF trapped = true
AND medical_emergency = true
THEN severity contribution = HIGH
```

Later, data-driven models can be evaluated.

---

# 30. Priority Feature Store

The system should derive normalized features such as:

```text
severity_score
victim_count
vulnerability_score
freshness_score
location_confidence
accessibility_score
corroboration_score
```

This allows the model/rules to evolve without rewriting ingestion.

---

# 31. Resource Recommendation Engine

For MVP:

> **Rule-based recommendation engine**

Example:

```text
Flood
+
Road inaccessible
+
Victims > threshold

→ Suggest rescue boat
```

The output should include the reasons.

---

# 32. Why Rule-Based First?

Because emergency resource recommendations require:

* explainability
* validation
* predictable behavior
* easy debugging
* domain review

A generative model should not decide:

> "Send three boats"

with no transparent reasoning.

# 34. NLP Model Strategy

The team should compare:

### Option A — Rules

Fast, deterministic.

### Option B — Traditional ML

Useful when labelled data exists.

### Option C — Transformer/NLP model

Better semantic understanding.

### Option D — LLM

Potentially useful for multilingual/unstructured interpretation.

The team must benchmark rather than automatically choose the most advanced model.

---

# 35. AI Decision Rule

Ask:

> **Does AI materially improve emergency information extraction compared with a rule-based baseline?**

If:

```text
Rules:
91% F1

AI:
92% F1

AI cost:
10×
```

then AI may not be justified.

If:

```text
Rules:
65% F1

AI:
89% F1
```

then AI provides a measurable advantage.

---

Example:

# 39. Deduplication Architecture

The deduplication engine should compare candidate events using:



# 40. Deduplication Safety

False merging is dangerous.

Therefore:

```text
High confidence
→ automatically link

Medium confidence
→ suggest relationship

Low confidence
→ keep separate
```

The exact thresholds must be benchmarked.

---

# 41. Clustering Architecture

Clustering should operate after evidence normalization and location processing.


# 42. Clustering Algorithm

DBSCAN is a reasonable MVP candidate because it can:

* identify spatial clusters
* avoid specifying number of clusters beforehand
* identify noise

But:

> **DBSCAN itself is not the innovation.**

```text
Writes blocked
       ↓
Events must not be silently discarded
       ↓

       ↓

```

# 66. Dashboard Failure

# 71. Architecture Decision — Monolith vs Microservices

## Decision

> **Use a modular monolith for the SIH MVP.**

### Reason

The dominant problem is:

> **proving operational intelligence**

not:

> **proving distributed systems engineering.**

# 72. Architecture Decision — Database

## Decision

> **Use PostgreSQL + PostGIS unless benchmarking or implementation constraints provide a strong reason otherwise.**

# 73. Architecture Decision — AI

### Reason

* database-backed jobs

Kafka is not required by default.

# 90. Final Architecture Definition

> **NETRA should use a modular, local-capable architecture centered on a transactional spatial database, with clear processing modules for ingestion, normalization, NLP, location intelligence, evidence fusion, deduplication, spatial clustering, priority calculation and resource recommendation. The SIH MVP should remain a modular monolith with lightweight asynchronous processing, while maintaining interfaces that allow individual components to be separated later if real scaling or deployment requirements justify it.**

# 91. Killer Architecture Insight

> **The architecture should be boring where it can be boring and sophisticated only where the problem actually demands sophistication.**

The sophistication belongs in:

* evidence fusion
* uncertainty handling
* multilingual extraction
* spatial reasoning
* prioritization
* resilience

Not in:

* unnecessary microservices
* infrastructure buzzwords
* distributed systems for their own sake
