# 11. Incident Intelligence

# NETRA — API Architecture

## 1. Purpose

Define how NETRA components and external systems communicate.

The API should expose system capabilities without exposing internal implementation details.

---

## 2. API Flow

External Sources
        ↓
Integration Layer
        ↓
NETRA Backend API
        ↓
Processing Modules
        ↓
Database
        ↓
Responder Dashboard

---

## 3. Core APIs

### Authentication

POST /api/v1/auth/login
POST /api/v1/auth/logout
GET  /api/v1/auth/me

### Events

POST /api/v1/events
GET  /api/v1/events/{id}

### Incidents

GET   /api/v1/incidents
GET   /api/v1/incidents/{id}
POST  /api/v1/incidents
PATCH /api/v1/incidents/{id}

### Evidence

GET /api/v1/incidents/{id}/evidence

### Priority

GET  /api/v1/incidents/{id}/priority
POST /api/v1/incidents/{id}/priority/override

### Zones

GET /api/v1/zones
GET /api/v1/zones/{id}

### Field Updates

POST /api/v1/incidents/{id}/field-updates
GET  /api/v1/incidents/{id}/field-updates

## 4. Event Ingestion

Example:

POST /api/v1/events

Input:

{
  "source_type": "SMS",
  "timestamp": "...",
  "text": "Family trapped in house",
  "location": {
    "lat": 19.076,
    "lon": 72.877
  }
}

Output:

{
  "event_id": "EVT-1024",
  "status": "RECEIVED"
}

---

## 5. Priority Override

Human responders can override system priority.

Input:

{
  "priority": "P1",
  "reason": "Field responder confirmed trapped victims"
}

Every override must be audited.

---

## 6. Field Update

Field responders can submit:

- verification status
- victim count
- medical condition
- access condition
- notes
- resource requirements

A field update may trigger priority recalculation.

---

## 7. API Security

Protected APIs must use:

- authentication
- role-based authorization
- HTTPS
- input validation
- rate limiting where required
- audit logging

External systems must not directly modify the database.

---

## 8. Error Handling

Use consistent errors.

Example:

{
  "error": {
    "code": "INVALID_LOCATION",
    "message": "Location could not be validated"
  }
}

Never expose internal stack traces.

---

## 9. Idempotency

Event ingestion must prevent uncontrolled duplicates.

The same event submitted repeatedly should be recognized using an event ID or idempotency key.

---

## 10. API Versioning

Use:

/api/v1/...

Breaking API changes should use a new version.

---

## 11. Integration Architecture

External systems connect through adapters:

External System
      ↓
Adapter
      ↓
Validation
      ↓
NETRA Event Model
      ↓
Processing

Possible future adapters:

- ERSS
- emergency location systems
- official disaster systems
- field systems
- SMS gateways

These integrations must not be assumed to already exist.

---

## 12. Reliability

APIs should support:

- timeouts
- safe retries
- idempotency
- structured errors
- correlation IDs
- health checks

If an external integration fails, NETRA's core system should continue operating where possible.

---

## 13. MVP API Scope

For the SIH prototype, prioritize only:

1. Authentication
2. Event ingestion
3. Incident retrieval
4. Evidence retrieval
5. Priority retrieval
6. Priority override
7. Zone retrieval
8. Field updates

Do not build unnecessary APIs.

---

## 14. Golden Rule

> The API must preserve the distinction between raw evidence, system-derived intelligence, and human-verified decisions.

RAW EVENT
    ↓
SYSTEM INTELLIGENCE
    ↓
HUMAN DECISION
