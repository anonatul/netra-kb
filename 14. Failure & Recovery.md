## 1. Connectivity State Machine (Judge-Critical)

Do NOT claim one mechanism works everywhere. NETRA operates in explicit connectivity states:

```text
NORMAL
  ↓
DEGRADED
  ↓
SEVERELY DEGRADED
  ↓
CELLULAR UNAVAILABLE
  ↓
LOCAL / ALTERNATIVE NETWORK
```

### NORMAL

All integrations + real-time ingestion + real-time dashboard.

### DEGRADED

SMS + emergency services + intermittent API. Incoming events delayed; timestamps preserved.

### SEVERELY DEGRADED

SMS + cached data + field updates. Local processing continues.

### CELLULAR UNAVAILABLE

NETRA becomes local command-center software. Ordinary SMS cannot be assumed to work. Data only from already-received records, local responder inputs, and separately validated alternative communication layers.

### LOCAL / ALTERNATIVE NETWORK

Dedicated responder-side infrastructure (radio/mesh/LoRa/satellite) — explicitly experimental, not "phones automatically connect."

## 2. Three Kinds of "Offline" (Do Not Mix)

| Mode | Meaning | NETRA capability |
| ---- | ------- | ---------------- |
| Offline A | Internet unavailable | Local dashboard/backend keeps working. Easy. |
| Offline B | Cellular data unavailable | SMS/voice may still work; infrastructure-dependent. |
| Offline C | No cellular infrastructure | Ordinary SMS does NOT work; needs alternative radio/mesh/satellite — separate layer, not MVP claim. |

## 3. Failure Register (Judge-Validated)

| Failure | Likelihood | Impact | Mitigation |
| ------- | ---------- | ------ | ---------- |
| Cellular tower completely destroyed | High | Critical | Don't depend on SMS; support alternative responder infrastructure |
| SMS congestion/delay | High | High | Timestamp + freshness scoring |
| Fake distress messages | Medium | High | Anomaly detection + confidence scoring |
| AI misclassifies emergency | Medium | Critical | Deterministic safety rules + human confirmation |
| Victim stops transmitting | High | High | Never equate silence with safety |
| AML/ELS unavailable | Medium | High | Multi-source location |
| GPS inaccurate | Medium | High | Confidence radius rather than exact pin |
| Dashboard loses internet | High | High | Local/offline operation |
| Telecom integration unavailable | High | Critical | Simulation adapter for MVP |
| Government won't deploy custom telecom | High | Critical | Architect as software layer over existing systems |

## 4. Component Failure Fallbacks

### AI failure

```text
AI unavailable → rule-based extraction → reduced confidence → human review
```

### Location failure

```text
No exact GPS → alternative location evidence → approximate area → lower confidence
```

Never fabricate a precise coordinate.

### Duplicate detection failure

```text
Possible duplicate → keep reports separate → link as related → human review
```

False merging is more dangerous than displaying duplicates.

### Priority engine failure

```text
Engine unavailable → severity rules + recency + manual operator sorting
```

### Recommendation failure

```text
Recommendation unavailable → priority remains available → responder chooses resources manually
```

### Dashboard failure

```text
Dashboard crashes → backend + database continue → logs preserved → restart dashboard
```

### Database failure

```text
Database unavailable → writes blocked → events must NOT be silently discarded
→ queue / local persistence → recovery
```

## 5. System Recovery Requirements

After restart, NETRA must recover:

- active incidents
- evidence
- priorities
- status
- pending updates
- audit records

Critical state must never exist only in volatile memory.

## 6. Sync After Reconnection

```text
Local changes → sync queue → central endpoint → validation
→ conflict detection → merge (preserve both, flag, human/defined policy)
```

Never silently overwrite field evidence.

## 7. Golden Failure Rule

> **Every stage has a safe fallback; no optional component is a single point of failure for the core emergency workflow. When uncertain: UNKNOWN + HUMAN REVIEW, never false certainty.**
