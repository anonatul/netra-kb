> **Purpose:** Define NETRA's complete operational workflow from incoming disaster evidence to responder action and field verification.

# 1. Workflow Objective

NETRA's workflow converts fragmented emergency information into an operationally useful rescue picture.

The complete conceptual loop is:

```text id="k3x3sy"
EMERGENCY
    ↓
INCOMING EVIDENCE
    ↓
INGESTION
    ↓
NORMALIZATION
    ↓
DEDUPLICATION
    ↓
INCIDENT EXTRACTION
    ↓
LOCATION + CONFIDENCE
    ↓
EVIDENCE FUSION
    ↓
SPATIAL CONSOLIDATION
    ↓
RESCUE PRIORITY
    ↓
RESOURCE RECOMMENDATION
    ↓
HUMAN RESPONDER DECISION
    ↓
FIELD ACTION
    ↓
FIELD VERIFICATION
    ↓
INCIDENT UPDATE
    ↓
REPRIORITIZATION
```

The system is therefore a **continuous feedback loop**, not a one-time classification pipeline.

NETRA may operate in a disaster context triggered by:

* official disaster information
* authorized operator activation
* emergency-system integration
* manual control-room activation
* simulation for testing

NETRA should not independently declare a national or regional disaster.

# 5. Stage 2 — Ingestion

The ingestion layer accepts the incoming record and creates an internal event.

```text id="0c4rko"
Incoming Source
      ↓
Validation
      ↓
Schema Conversion
      ↓
Internal Event
```

---

## Ingestion Validation

Check:

* source format
* timestamp
* required fields
* malformed data
* authentication where applicable
* duplicate transport events
* message size
* rate limits

Invalid records should not silently disappear.

They should be logged and handled through an error path.

# 7. Stage 3 — Normalization

Different sources use different schemas.

NETRA converts them into a common internal event representation.

Example:

```text id="y4e4yx"
SOURCE RECORD
      ↓
NORMALIZED EVENT

{
  source_type,
  timestamp,
  location,
  text,
  source_identifier,
  metadata
}
```

The normalized representation should preserve the original evidence reference.

---

# 8. Stage 4 — Deduplication

NETRA checks whether the incoming report is:

1. exact duplicate
2. near duplicate
3. related to an existing incident
4. independent evidence
5. unrelated new incident

Potential signals:

```text id="dx3p4g"
Time
+
Location
+
Text similarity
+
Source relationship
+
Incident attributes
```

---

## Example

```text id="3i1r5a"
Report A:
"We are trapped in our house."

Report B:
"Family trapped near the bridge."

Report C:
"Water entered the house."

Location:
Same 80m area

Time:
Within 3 minutes
```

NETRA may determine:

> **Potentially related incident cluster**

rather than automatically treating all three as separate incidents.

---

# 9. Important Deduplication Rule

Deduplication must **not destroy evidence**.

Instead:

```text id="q0o4z6"
Raw Reports
    ↓
Linked to Incident
    ↓
Evidence retained
```

The system should preserve:

* original report
* source
* timestamp
* location
* processing history
* relationship to incident

# 11. AI Processing

The AI/NLP layer may perform:

* language identification
* multilingual understanding
* severity extraction
* vulnerability extraction
* victim count estimation
* condition extraction
* resource requirement extraction
* location/entity extraction from text

---

## AI Safety Rule

AI output is evidence, not absolute truth.

Every model output should ideally have:

```text id="o2a5v4"
Prediction
+
Confidence
+
Model Version
```

Example:

```text id="e5q2bc"
Vulnerable Person:
ELDERLY

Confidence:
0.94

Model:
NETRA-NLP-v1
```

# 14. Location Uncertainty Rule

NETRA must never pretend uncertain locations are exact.

Instead of:

```text id="2i9f4m"
Victim = exact coordinate
```

the system should represent:

```text id="s3u8h2"
Estimated incident area
+
uncertainty radius
```

This is particularly important when location information comes from:

* approximate cell location
* manually entered locations
* text descriptions
* low-quality GPS

# 16. Incident Confidence

Conceptually:

```text id="h7r6kw"
Incident Confidence

Source Reliability

+

+
Temporal Consistency
+
```

# 17. Stage 8 — Spatial Consolidation

Related incidents may be grouped into operational zones.

NETRA should consider:

* spatial distance
* location uncertainty
* report density
* disaster context
* geographic structure

The system should not blindly use a fixed 50m radius.

---

# 18. Adaptive Clustering

Potential logic:

```text id="l0g4if"
High-accuracy GPS
      ↓
Smaller cluster tolerance

Low-accuracy location
      ↓
Larger uncertainty-aware tolerance
```

DBSCAN may be used as an implementation component.

Other approaches can be evaluated.

This is the core operational stage.

NETRA calculates priority using factors such as:

```text id="evp0n7"

+

+

+
```

---

# 21. Priority Explainability

Every high-priority result must have an explanation.

Bad:

> P1 because AI says so.

Good:

```text id="0j9q6y"
P1 because:

+ 5 critical medical indicators
+ 32 estimated victims
+ 7 vulnerable people
+ recent reports
+ 92% location confidence
+ road access blocked
```

The responder must be able to inspect the underlying evidence.

# 22. Stage 10 — Resource Recommendation

Based on incident attributes, NETRA may recommend resources.

Example:

```text id="o9v8b2"

32
```

---

## Recommendation Principle

The system must distinguish:

> **Suggested resources**

from:

> **Required resources**

The former is decision support.

The latter would imply certainty that NETRA cannot guarantee.

---

# 23. Resource Recommendation Methods

The MVP should initially prefer:

### Rule-based recommendation

```text id="9q6d5m"

+

```

This is explainable and easy to validate.

AI can later assist with more complex recommendations.

# 33. Connectivity Degradation Workflow

NETRA should operate according to connectivity state.

## Mode A — Normal

```text id="4r8l7j"
All available integrations
↓
Real-time ingestion
↓
Real-time dashboard
```

## Mode B — Intermittent Connectivity

```text id="6s5l1y"
Incoming events may be delayed
↓
Timestamp preserved
↓
Freshness adjusted
↓
Local processing continues
```

## Mode C — Internet unavailable at command centre

```text id="0l3jqp"
Local backend
+
Local database
+
Local dashboard
```

## Mode D — Cellular infrastructure unavailable

```text id="x9q4h7"
Ordinary SMS cannot be assumed.

NETRA continues only with:
- already received data
- local responder inputs
- separately validated alternative communication infrastructure
```

---

# 34. Important Communication Principle

NETRA must distinguish:

> **Application offline**

from:

> **Communication infrastructure offline**

The first can be solved through local software.

The second cannot be solved merely through Docker or an offline database.

---

# 35. Failure Path — AI Failure

If NLP is unavailable:

```text id="7g9b1c"
AI unavailable
     ↓
Fallback rules
     ↓
Basic structured extraction
     ↓
Human review for uncertain cases
```

An AI outage must not stop emergency processing.

---

# 36. Failure Path — Location Failure

If exact location is unavailable:

```text id="5r7g9x"
No exact GPS
     ↓
Alternative location evidence
     ↓
Approximate area
     ↓
Lower confidence
```

The system should never fabricate a precise coordinate.

---

# 37. Failure Path — Duplicate Detection Failure

If duplicate detection is uncertain:

```text id="x4d8s3"
Possible duplicate
     ↓
Keep reports separate
     ↓
Link as related
     ↓
Human review
```

False merging can be more dangerous than displaying duplicates.

---

# 38. Failure Path — Priority Engine Failure

If the priority engine fails:

```text id="m7r2n4"
Priority engine unavailable
        ↓
Fallback:
Severity rules
+
Recency
+
Manual operator sorting
```

NETRA must degrade gracefully.

---

# 39. Failure Path — Dashboard Failure

If the dashboard crashes:

```text id="s4c7q2"
Dashboard unavailable
        ↓
Backend/database remain active
        ↓
Logs preserved
        ↓
Restart dashboard
```

The architecture should avoid data loss.

---

# 40. Failure Path — False Reports

NETRA should not automatically trust report volume.

Potential checks:

```text id="p8h6z3"
Unique sources
+
Spatial consistency
+
Temporal patterns
+
Semantic similarity
+
Known source reliability
```

Potentially suspicious patterns should be flagged.

---

# 41. Failure Path — Conflicting Reports

Example:

```text id="a3q6j8"
Report A:
Road blocked

Report B:
Road accessible
```

NETRA should not silently choose one.

Instead:

```text id="k9v2m1"
CONFLICTING EVIDENCE

Latest report:
10:42

Previous report:
10:35

Confidence:
Medium
```

The responder can inspect the evidence.

---

# 42. Failure Path — Sudden Report Burst

Suppose:

```text id="5v2d6w"
10 reports/min
       ↓
500 reports/min
```

NETRA should:

* buffer events
* preserve timestamps
* avoid duplicate processing
* maintain priority ordering
* prevent dashboard overload

The exact message-broker technology is an implementation decision, not a product requirement.

---

# 49. Workflow Anti-Patterns

NETRA should avoid:

### ❌ AI as a single point of failure

If AI fails, the emergency pipeline must continue.

### ❌ Exact-looking uncertain locations

Never hide uncertainty.

### ❌ Automatic safety inference

No signal ≠ safe.

### ❌ Automatic autonomous dispatch

Human decision required.

### ❌ Silent evidence deletion

Preserve raw evidence.

### ❌ Fixed clustering radius without justification

Use uncertainty-aware clustering.

### ❌ Technology-driven workflow

Workflow requirements determine technology.

# 51. Final Workflow Definition

> **NETRA's core workflow is a continuous evidence-to-decision loop: incoming emergency information is normalized, consolidated, interpreted, geolocated and confidence-weighted; related information is transformed into operational zones; zones are prioritized using severity, vulnerability, freshness, confidence and accessibility; responders receive explainable recommendations; field verification feeds back into the system to continuously update the operational picture.**

---

# 52. Golden Workflow Principle

> **Every NETRA decision must be traceable from responder recommendation back to the evidence that produced it, and every stage must have a safe fallback when its preferred technology fails.**
