# NETRA — Data Architecture

## 1. Purpose

Define how NETRA stores, relates, and tracks emergency information.

Core principle:

> Raw evidence, system-derived intelligence, and human decisions must remain distinguishable.

---

## 2. Core Entities

NETRA uses these primary entities:

- Disaster
- Event
- Evidence
- Incident
- Operational Zone
- Priority
- Recommendation
- Field Update
- User
- Audit Log
- Model Version
- Rule Version

---

## 3. Event vs Incident

### Event

An individual incoming observation.

Examples:
- SMS
- emergency location
- citizen report
- field report

### Incident

A consolidated representation of a real-world emergency.

One incident can contain many events.

```text
Event 1 ─┐
Event 2 ─┼──> Incident A
Event 3 ─┘
```

---

## 4. Entity Details

### Disaster

```text
disaster_id, type, affected_geography, activation_time, severity_context, operating_mode
```

### Event (raw, immutable)

```text
event_id, source_type, source_timestamp, received_timestamp, text, location, metadata
```

### Evidence (source-linked)

```text
source, timestamp, content_reference, location, extraction_results, confidence, relationship
```

### Incident (consolidated)

```text
incident_id, disaster_id, status, location, location_confidence,
severity, victim_estimate, vulnerability, confidence,
priority, evidence_refs, zone_id, created_at, updated_at
```

### Operational Zone

```text
zone_id, geometry, incidents, evidence_count, independent_source_count,
confidence, priority, status, updated_at
```

### Priority Score (versioned)

```text
incident_id, score, level (P1–P4), reasons, rule/model_version, timestamp
```

### Recommendation (explainable)

```text
incident_id, resources, reasons, rule_version, status (SUGGESTED / ACCEPTED / REJECTED)
```

### Field Update

```text
incident_id, user, update_type, values, timestamp, status (VERIFIED / RESCUED / FALSE / ...)
```

### Audit Log

```text
user, action, target, previous_value, new_value, reason, timestamp
```

---

## 5. Relationships

```text
Disaster 1───N Incidents
Incident 1───N Events (via Evidence links)
Incident N───1 Zone
Incident 1───N PriorityScores (history, versioned)
Incident 1───N Recommendations
Incident 1───N FieldUpdates
Evidence 1───1 Event (provenance preserved)
```

Events are never deleted; they are linked, superseded or flagged.

---

## 6. Data Classes (Never Conflate)

```text
RAW       — what was reported (citizen text, signal, field note)
DERIVED   — what the system inferred (severity, vulnerability, confidence)
SYSTEM    — what the system decided (priority, recommendation)
HUMAN     — what a responder decided (override, verification, rescue)
```

---

## 7. Independent Evidence Counting

```text
Reports: 84
Unique devices: 31
Estimated victims: 46
Independent corroborations: 14
Confidence: 92%
```

Report count ≠ victim count ≠ independent evidence count.

---

## 8. Spatial Data

- locations stored as geometry with accuracy/confidence
- PostGIS GIST indexes on incident locations and zone geometries
- uncertainty represented as radius, never false precision

---

## 9. Time Handling

- UTC internally
- local timezone for display
- explicit source_timestamp and received_timestamp
- ingestion order ≠ event order (out-of-order handling required)

---

## 10. Versioning

- AI outputs store model name + version + timestamp + confidence
- priority/recommendation rules store rule version
- historical decisions remain associated with the version that produced them

---

## 11. Retention

- configurable, law/organization-aligned
- original evidence retained per policy for audit
- no silent deletion of emergency evidence

---

## 12. Golden Data Rule

> **Preserve raw evidence, distinguish data classes, and never let a message count stand in for an independent victim count.**
